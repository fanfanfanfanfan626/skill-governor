# Usefulness and evaluation

A skill is useful when it improves the user's outcome enough to justify selection, reading, execution and maintenance cost. Avoid a universal numeric score or popularity proxy.

| Assessment | Evidence needed | Consequence |
|---|---|---|
| useful | Distinct capability or demonstrated improvement on relevant tasks | Keep and route precisely |
| conditional | Benefit depends on project, tool, stage or task size | Encode the condition |
| redundant_candidate | Another workflow appears to cover the same need with equal or better evidence | Compare before any authorized consolidation |
| unsupported | Required platform/tool/resources unavailable in this environment | Report limitation and authorized fallback |
| unassessed | Insufficient evidence | Do not invent a verdict |

Record information value, technical correctness, actual tool readiness, task outcome, workflow cost and user acceptance separately where relevant. A reliable local checker cannot validate the quality of a financial model, rendered slide or deployed app by inspecting file existence.

## Scenario evaluation

Choose realistic prompts covering positive selection, no-skill work, overlapping skills, project boundaries, plan-only scope, stage changes, explicit skill requests, missing dependencies, conflicting rules, provider mismatch and updates. Define acceptable outcomes before inspecting results. Several primary/companion combinations may be valid if they preserve scope and required gates.

For before/after claims, compare the same or equivalent tasks, inputs, model/host configuration and validation criteria. Measure outcome quality first, then unnecessary calls/reads and cost. Record sample size and variation; do not claim reduced tokens from a shorter description alone. Keep failed cases.

Use an independent evaluator for complex or consequential governance when available and authorized. Provide the skill, raw scenarios and necessary fixtures without preferred answers. An independent qualitative routing review is not a measured success rate. Live external actions need their own authorization; fixture-only tests must be labeled accordingly.

## Evidence states

Keep source reviewed, referenced paths checked, helper tested, scenario evaluated, real workflow exercised and user accepted distinct. A hash binds evidence to a version; it does not certify the reviewer or model's understanding. Record precise failures, fixes and remaining limitations. Do not remove a rare but required project safeguard because it has few recent invocations.
