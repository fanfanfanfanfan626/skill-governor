# Setup and generated policy

First resolve the request: explain, audit, plan, or implement. If scope is clear, proceed; ask only for missing information that changes the authorized outcome. A user saying to set up governance generally authorizes reversible state creation and the identified integration, not publication or deletion of existing skills. Keep an audit-only request read-only except its requested report.

## Discovery

First inspect the existing governance entrypoint and state, if any. Reuse and reconcile an adopted policy instead of creating a competing global policy. Never replace another tool's managed block or adopt an unowned block. If a compatible state already exists, use lifecycle commands rather than initializing a second catalog.

Inspect the host's current catalog and documented skill roots. Pass explicit namespace/path pairs to the initializer. Each root may be a single skill folder or a direct container of skill folders. Nested system/plugin roots need separate entries. Do not recursively search unrelated projects. If multiple cached plugin versions exist, establish the active version from host evidence before registering it; a folder listing does not establish activity.

Use namespaces such as personal, team or an actual plugin identifier so equal skill names do not silently merge. Missing, malformed and duplicate entries should be surfaced. External or runtime-owned skills that cannot be read as files can be documented in the plan with their provider and verification limit; do not invent filesystem copies.

If the library is empty, record that finding and give a minimal no-skill/addition policy. Do not fabricate entries to initialize the helper: its initializer requires at least one actual source. Defer the catalog until a source exists, or use the instruction-only workflow in hosts.md.

## Tailored outputs

The initializer creates private `sources.json`, `.gitignore` and a draft `PLAN.md` under the supplied state directory. It does not classify skills by keywords or certify them. `registry.json` is generated by refresh/check workflows. Its initial unreviewed state is expected.

Read actual entrypoints and fill routing annotations in sources.json: domain, role, use_when, avoid_when, required_reads (with conditions), companions, value, value_reason and value_evidence. Use complete sentences or explicit criteria, not giant keyword lists. User-owned annotations are separate from source descriptions and are not written into vendor skills.

Write the tailored operating policy to `POLICY.md` in this state directory, with:

- current project/host boundaries and selection priority;
- optional/no-skill cases and stage transitions;
- scoped trigger and exclusion rules for actual overlapping skills;
- exact mandatory/conditional pre-reads and tool gates;
- missing capabilities and authorized fallbacks;
- lifecycle and evidence instructions;
- links to focused domain rules only when needed.

The generic entrypoint in this package is a model for the policy, not a substitute for reading the user's actual sources. Preserve existing good project rules. For a small library use one concise table; larger libraries can use a short index and focused domain files.

## Adoption and integration

The marked host pointer is installed by `integrate` only after POLICY.md exists. `--dry-run` previews the exact proposed change. The tool preserves pre-existing bytes outside its own block, refuses malformed/nested/ambiguous blocks, records backups and verifies state paths. Do not integrate a draft report as an adopted policy.

Select the host instruction file by documentation or explicit user choice. Do not write both global and repository instructions merely because both files exist. A project-scoped entry is usually enough for a project request; global changes require global scope. No hidden daemon or cron job is added.

Test ordinary, boundary, negative, missing-dependency and update cases. Record the evidence and limitations. An agent-created coherent policy is a candidate until its behavior is exercised; successful integration alone is not a usefulness result.
